# Работа 4. Управление доступом

Егоров, группа 16М-нф26. Сервис — электронный журнал.

## Матрица минимальных прав

| Роль и задача | Своя оценка | Оценки своей кафедры | Роли | Настройки |
|---|---|---|---|---|
| Студент: посмотреть результат | Читать | — | — | — |
| Преподаватель: вести назначенную группу | — | Читать, изменять | — | — |
| Методист: проверить ведомость | — | Читать | — | — |
| Администратор: обслуживать систему | — | — | Управлять | Управлять |

RBAC задаёт действия роли. Дополнительные условия ABAC: кафедра пользователя должна совпадать с кафедрой ведомости; изменение или управление разрешено только с управляемого устройства. Для студента дополнительно проверяется владелец записи. Отключённому аккаунту запрещено всё, отсутствующее разрешение означает отказ.

В учебных CSV кафедра используется как граница для групп. В настоящем журнале её одной мало: нужна ещё явная связь преподавателя с назначенной группой.

## Проверка запросов

Команда: `python 04_access/evaluate_access.py`. Результат с причинами: [decisions.csv](decisions.csv).

| Запрос | После исправления | Причина |
|---|---|---|
| R01 student1 читает grade_s1 | ALLOW | Своя оценка |
| R02 student1 читает grade_s2 | DENY | Чужая оценка |
| R03 teacher1 изменяет group_cs | ALLOW | Своя кафедра, управляемое устройство |
| R04 teacher1 обращается к другой кафедре | DENY | Кафедры различаются |
| R05 teacher2 изменяет group_math | DENY | Устройство неуправляемое |
| R06 methodist1 читает group_cs | ALLOW | Чтение своей кафедры |
| R07 methodist1 читает другую кафедру | DENY | Кафедры различаются |
| R08 student1 управляет ролями | DENY | У студента не должно быть такого разрешения |
| R09 admin1 управляет настройками | ALLOW | Разрешение администратора и управляемое устройство |
| R10 former1 изменяет ведомость | DENY | Аккаунт отключён |

Лишнее разрешение в исходной таблице — `Student,RoleConfig,manage`. До удаления модель допускала R08, после — запрещает. Проверка R02 показывает, что одного успешного входа недостаточно для чтения чужих данных.

## Создание, смена роли и увольнение

При создании аккаунта руководитель согласует роль и кафедру, служба аккаунтов выдаёт минимальные права и подключает MFA. Затем проверяются разрешённое и запрещённое действия.

В `identity_events.csv` у teacher1 есть переход Teacher → Methodist, а в `users.csv` ещё стоит Teacher. Это несогласованность снимков, поэтому решения выше относятся к исходному `users.csv`. В отдельной модели после смены роли чтение group_cs разрешено, запись запрещена: [role_change.txt](role_change.txt). Старое разрешение записи нужно отозвать, а не просто добавить новую роль.

У teacher2 состояние устройства Pending: считать его управляемым пока нельзя. У former1 аккаунт отключён, но сессии не отозваны. Нужно отозвать их вместе с токенами, убрать группы и проверить отказ старому токену. В работе проверена модель по CSV.

## Журнал аудита

Для каждой попытки: время UTC, пользователь, роль, объект, действие, ALLOW/DENY, причина, устройство и идентификатор запроса. Для смены прав дополнительно: прежняя и новая роль, кто согласовал и выполнил изменение. Пароли и токены в журнал не записываются. Служба ИБ проверяет отказы к чужим объектам и несогласованные изменения ролей.
